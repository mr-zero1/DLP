# NEON SENTINEL backend (Phase 1)

This minimal Flask service keeps endpoint registrations and heartbeat timestamps
in SQLite. It does not connect to or replace the desktop UI's `MockService`.

## Run on the lab network

From the project root, activate the existing virtual environment, configure a
private bearer token, then start the server:

```bash
source .venv/bin/activate
export NEON_SENTINEL_API_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
python -m backend.main
```

By default the service listens on `192.168.122.1:5000` and stores its database
at `~/.local/share/neon-sentinel/devices.sqlite3`. Override settings with
`NEON_SENTINEL_HOST`, `NEON_SENTINEL_PORT`, and `NEON_SENTINEL_DB_PATH`.
Keep the API token secret and use HTTPS when exposing the service beyond a
trusted lab network. Health checks remain unauthenticated at
`GET /api/v1/health`.

## Device API

All device routes require `Authorization: Bearer <NEON_SENTINEL_API_TOKEN>`.
Registration accepts a stable UUID generated by the enrolling client:

```http
POST /api/v1/devices/register
Content-Type: application/json

{"device_id":"d9428888-122b-4c1c-8a47-4a2d0ca8f3d9","hostname":"lab-pc-01","platform":"Windows 11"}
```

The API returns `201` with the stored device, or `409` if that UUID already
exists. `POST /api/v1/devices/<device_id>/heartbeat` updates its UTC
`last_seen_at` value. `GET /api/v1/devices` returns all registered devices.
Malformed data returns `400`, unknown devices return `404`, and missing or
incorrect credentials return `401`. If no API token is configured, device
routes fail closed with `503`.

## Event ingestion (Phase 2.2A)

`POST /api/v1/events/batch` uses the same Bearer Token authentication as the
device API. Send a JSON object containing 1–100 events; each event must have
exactly these fields:

| Field | Contract |
|---|---|
| `event_id` | UUID identifying this event |
| `device_id` | UUID of a device already registered with this server |
| `event_type` | Non-empty string, at most 100 characters |
| `severity` | One of `info`, `low`, `medium`, `high`, or `critical` |
| `occurred_at` | ISO 8601 timestamp with a timezone |
| `metadata` | JSON object, at most 8 KiB when encoded as UTF-8 |

Example request:

```http
POST /api/v1/events/batch
Authorization: Bearer <configured-token>
Content-Type: application/json

{
  "events": [{
    "event_id": "d9428888-122b-4c1c-8a47-4a2d0ca8f3d9",
    "device_id": "68f99a35-7722-48f5-a055-dc2a872a9f28",
    "event_type": "demo",
    "severity": "info",
    "occurred_at": "2026-01-02T03:04:05.123Z",
    "metadata": {"source": "agent", "purpose": "synthetic demonstration"}
  }]
}
```

The request body is limited to 64 KiB. Raw file contents are neither required
nor part of the event contract; do not put sensitive contents in `metadata`.
Accepted events are committed to the server's `events` table before the
response is sent. The response explicitly identifies event IDs safe for the
client to mark as sent:

```json
{
  "acknowledged_event_ids": ["d9428888-122b-4c1c-8a47-4a2d0ca8f3d9"],
  "rejected_events": []
}
```

An event already stored for the same device is acknowledged again, making
retries idempotent. If an event ID belongs to another device, that ID is not
acknowledged and appears in `rejected_events` with
`event_id_owned_by_another_device`; the original event and owner are unchanged.
Malformed input and invalid batch sizes return `400`, unregistered devices
return `404` without accepting the batch, unauthenticated requests return
`401`, and oversized requests return `413`.
